# Claude design workflow

Use Claude for layout, visual direction, new reusable page types, accessibility, or real feature work. Use Sanity for routine content.

The Studio navigation includes **Design with Claude**. It begins with one conversational question: **“Shelly, what do we want to change today?”** Shelly can write naturally, then optionally identify a page or add reference images. Studio copies a bounded request and opens Claude Code. Studio remains Shelly's front door while the safety mechanics stay in the background.

## Good Claude request

> Make the French Series collection page feel more editorial. Preserve the existing typography and color tokens, keep collection membership CMS-owned, support long titles, and verify mobile and desktop. Do not deploy; show me the checked change first.

## Request template

> Change: [describe the visual or functional outcome].
>
> Preserve: the current brand, editable content, artwork addresses, accessibility, and hosting arrangement.
>
> CMS fields involved: [name them if known, or ask Claude to identify them].
>
> Verify: mobile, desktop, long/empty optional content, `npm run check`, and a Cloudflare build when infrastructure is touched.
>
> External actions: [none / deploy only after I approve / other explicit permission].

Claude must read `CLAUDE.md`, `docs/DESIGN_SYSTEM.md`, and `docs/CMS_SCHEMA.md` before editing. Schema changes require a migration-compatible update across schema, queries, types, tests, and documentation.

## The safe publishing reminder carried into Claude

Every brief generated by Studio tells Claude to carry the change through these client-facing checkpoints:

1. Shape and check the requested change safely in the background.
2. Prepare a review version and share the review link.
3. Explain what changed in plain language.
4. Stop for Shelly's explicit approval.
5. After approval, publish the approved change.
6. Confirm that the website is live and working.

Claude uses the status language **shaping the idea**, **preparing your review**, **ready for your review**, **waiting for your approval**, **publishing**, and **live and checked**. The safety work happens in the background; Claude does not ask Shelly to manage it or describe it with developer terminology.

## Recovery boundaries

- Every published change remains recoverable in the site's protected history.
- A weekly code snapshot marks the current live version and keeps a complete recovery copy for 90 days.
- The hosting history provides another live-site recovery layer.
- Sanity document history and the weekly dataset export protect content separately from code.
